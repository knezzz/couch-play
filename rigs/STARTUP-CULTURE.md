# CouchPlay team culture

CouchPlay is a living-room party console: an Android TV app shows the game, and phones join by QR code and play in the
browser. Everything is Flutter. The design is `docs/specs/2026-11-13-couchplay-design.md`; the build plan is
`docs/plans/2026-11-13-couchplay.md`. Read both before your first task. They are the source of truth: if code and
plan disagree, say so to your lead instead of quietly picking one.

## How the work flows

- The PM owns the plan and `docs/STATUS.md`, and talks to the person. The tech lead routes engineering work.
- Work moves as queue tasks (`rig queue`), one plan task or less per queue task. A `rig send` message informs; a queue
  task is work someone owns. When you finish, hand the task back with what you ran.
- Follow the plan's steps in order: failing test, see it fail, implement, see it pass, commit.
- **Task 5 is a gate.** Nothing after Task 5 starts until the person has seen the real-TV performance numbers and said
  go. Task 13 also stops for the person to review the Croatian Međimurje pack.

## Ship small

- Build the smallest version that does the job, then stop. Name what you left out in one line instead of building it.
- No options, abstractions or "for later" code the plan doesn't ask for.
- Every "done" says what you ran and what you did not check. Say "verified" only if you ran it.
- A clean result is a fine result. Don't create work for an idle seat.

## The checkout

- Everyone works in the main checkout at the repo root, on `main`. No worktrees unless the lead says several seats are
  editing the same package at once.
- Commit by explicit path (`git commit -- <paths>`). Changes you didn't make belong to someone else. A path commit
  takes the whole file, so if another seat has unfinished edits in it, ask them first.
- Don't switch branches, stash or reset. Don't run `dart format` on files you didn't write.
- `apps/tv/assets/controller.zip` is generated by `tool/build_controller.sh`; never commit it.

## This machine

- Intel Mac (x86_64). Xcode, Android Studio and Flutter 3.47.7 (through fvm) are installed.
- Check `df -h` before emulator or release builds. A nearly full disk makes installs hang without an error.
- Run Gradle as `./gradlew --no-daemon` if you run it directly.
- The Pixel 6a (adb device `28051JEGR09026`) is the person's own phone. Never install to it or drive it. Phones only
  ever open the controller in their browser.
- The Android TV is the person's. Connecting to it over adb (Task 5 and Task 14) needs the person's yes each session;
  the PM asks.

## Ask the person first

Installing anything system-wide (Homebrew casks, SDK packages), pushing, PRs, merges and tags. Tell the PM, who asks.
Never put secrets or credentials in messages or commits.

## When something goes wrong

- Blocked on a peer: tell them with `rig send`, then your lead. Don't stall silently.
- Failing test you can't explain: use systematic debugging, don't guess-patch. After two failed attempts, tell your
  lead with what you tried.
- After startup or compaction: run `rig whoami --json`, then `rig queue list --destination <you> -a` to find what you
  own, then re-read the plan task you were on.

## Commands that don't stop the person

Keep commands plain so they run without approval: run `rig` commands as they are, without pipes or `$VARIABLES`, write
files with your file tool rather than a heredoc, and run one plain command at a time.
